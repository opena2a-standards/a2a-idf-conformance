# Reference verifiers and suite tooling

Reference tooling for producing and consuming A2A-IDF conformance fixtures.

## Shipped

- [`verify.mjs`](./verify.mjs) — Node.js verifier. Pure Node stdlib (`node:crypto`), no third-party dependencies. For composition fixtures it reconstructs the RFC 9421 signature base, applies the Envoys §4.3 tag rule (`a2a-message` or an absent tag accepted, any other tag rejected as `TAG_MISMATCH`), extracts the public key per A2A-IDF §6 dual-shape keyid resolution (`application/did+json` → DID Document with `Ed25519VerificationKey2020` + `publicKeyMultibase` or `JsonWebKey2020` JWK; else compact-form PEM SPKI), and verifies the Ed25519 signature. For level fixtures it evaluates the A2A-IDF §1 identity declaration (shape, DNS TXT binding, registry attestation over the RFC 8785 JCS form, validity window).
- [`verify.py`](./verify.py) — Python verifier. Single dependency: the [`cryptography`](https://pypi.org/project/cryptography/) package. Same interface, same check order, and same accept/reject/category decisions as the Node verifier on every fixture. It derives the provider domain of a Level 1 card with its own implementation of the WHATWG URL host rules; what that implementation approximates is listed under [Provider domain](../fixtures/levels/README.md#provider-domain).
- [`generate-fixtures.mjs`](./generate-fixtures.mjs) — deterministic fixture generator. Rewrites the fixtures and vectors it owns, every JSON file under `fixtures/` and `vectors/` except the two snapshot fixtures in [`fixtures/composition/hippo-rfc9421/`](../fixtures/composition/hippo-rfc9421/), from the RFC 8032 §7.1 seeds and the templates in the script, then writes `MANIFEST.sha256` from the JSON files under `fixtures/` and `vectors/` as it finds them. Self-checks that the composition signatures byte-match the pinned Envoys §14 vectors. CI reruns it and then runs `git diff --exit-code` (the byte-pin step), so a committed fixture that differs from what the script writes for it fails CI. The two snapshot fixtures are pinned in `MANIFEST.sha256` but not regenerated: the generator pins them as found, so the byte-pin step fails when one of them changes without `MANIFEST.sha256` and passes when the change is committed together with the refreshed `MANIFEST.sha256`.
- [`parity/parity.py`](./parity/parity.py) — cross-implementation parity gate. Runs both verifiers, plus any implementation added with `--verifier NAME=COMMAND`, over the fixture set and fails on any disagreement in gate status, verdict, or reject category, or on any observed outcome that differs from the fixture's pinned outcome. See [Testing another implementation](#testing-another-implementation). [`docs/captures/parity.txt`](../docs/captures/parity.txt) holds what it prints for the committed fixture set, the full output behind the trimmed excerpt in the top-level `README.md`, and [`docs/captures/parity.json`](../docs/captures/parity.json) holds the `--json` report of the same run; refresh both from the repository root with `python3 scripts/parity/parity.py --json docs/captures/parity.json > docs/captures/parity.txt`.
- [`conformance_profile.py`](./conformance_profile.py) — generates (or `--check`s) `conformance.json`, the machine-readable profile derived from the fixtures. `--check` also fails when a coverage claim in the top-level `README.md` or in `docs/coverage.md` names an envelope that `notCovered` still lists, unless the claim marks it "(unverified)", when `README.md`, `docs/coverage.md` or `fixtures/composition/README.md` says the suite composes with an adjacent layer (wire signature, identity claims, delegation/continuity) that no fixture under `fixtures/composition/` carries a `spec` entry for, and when the "at present" fixture count in the `COSIGNERS.md` baseline row differs from the number of fixtures. A fixture that is not UTF-8 text, or that Python's `json` module rejects with a syntax error, or that holds `NaN`, `Infinity` or `-Infinity` (which that module reads as numbers unless told not to, and which are not valid JSON), or that parses to a value other than a JSON object, or that lacks a field the profile is derived from (`name` and `description`, strings; `spec`, an array; `expected`, an object) or has one of another JSON type, is reported in one line naming the file and every such field, with exit code 1, in both modes. So is a fixture that may be valid JSON and that the script cannot read, or whose requirement entry it cannot write. The line names the cause: nesting too deep for the `json` module of the running Python to parse or, in a value the entry is derived from (`name`, `description`, `spec`, and the `verifyResult` and `rejectCategory` of `expected`), to write (the depth differs between Python versions; below it the fixture is profiled); an integer of more digits than Python converts (4,300 by default); a number in such a value too large for a Python float, such as `1e400`; or a lone surrogate in such a value, which UTF-8 cannot encode. For the first three the line says that this is a limit of the script, not a JSON error. The script reads fixtures and documents and writes the profile as UTF-8 whatever the locale, and regeneration encodes the whole profile before it opens `conformance.json`, so a run that reports a fixture leaves the file as it was. A `spec` entry of a composition fixture that is not a JSON object names no adjacent layer.
- [`check-doc-links.mjs`](./check-doc-links.mjs) — documentation path check. Fails when a relative link in a tracked Markdown file, or the script path of a `node` / `python3` command in one of its code blocks (including a command chained after `&&`, `||`, `;` or `|`), does not resolve. Command script paths may be relative to the Markdown file's directory or to the repo root, after any `cd <dir>` or `cd -- <dir>` earlier on the same line (a redirection on the `cd` is set aside, whether written as its own word, as in `cd fixtures 2>/dev/null`, or against the directory, as in `cd fixtures>/dev/null`, and whether or not its target is a `<placeholder>`, as in `cd fixtures 2><log>`). In a code block labelled as shell (`bash`, `sh`, `zsh`, `ksh`, `shell`, `console`, `shell-session`, `sh-session`, in any letter case), a `cd` inside a subshell, as in `(cd <dir> && node ...)`, applies up to the closing parenthesis; other blocks do not split at parentheses, so in them a `cd` that opens a subshell (`(cd <dir>` at the start of the line or after a blank, `=`, `$`, `<` or `>`, as in `$(cd <dir>` and `<(cd <dir>`) is one the check cannot resolve: the commands from it to the parenthesis that closes the subshell are not checked, and the commands before the subshell and after it are checked as if it were not there (put such a line in a shell-labelled block to have the commands inside checked). A `cd` the check cannot resolve (an option such as `-P`, a variable, `~`, `-`, a `<placeholder>` in the directory, such as `<your-clone>`, more than one operand, a path longer than 4096 characters, or any `cd` past the 32nd on one line) skips the commands it would move. It also fails when a file that a `cosign sign-blob` command writes is ignored by git in the `.sigstore/<org>/` directory the same code block says to commit it under. In a code block, text from an unquoted `#` that starts a word is a comment: the command script paths and cosign output flags in it are not read, the `.sigstore/<org>/` directory is. Run `node scripts/check-doc-links.mjs` from the repository root; from another directory, adjust the script path (for example `node ../../scripts/check-doc-links.mjs` from `fixtures/levels/`). The result does not depend on the working directory. Needs a git checkout: it reads the list of tracked Markdown files from `git ls-files`.
- [`test/`](./test/) — regression tests for the tooling above, on scratch copies and fixture variants that cannot be committed under `fixtures/`, and for the install commands in this README, the top-level one and `COSIGNERS.md`, which they run in a scratch directory to check that `pip install` runs inside the virtual environment the commands create. Run `node --test scripts/test/*.test.mjs` from the repository root (needs `git`, `bash`, and `python3` with `cryptography` and the `venv` module).

## Install

The Node tooling needs no install — it runs on stock Node ≥ 18:

```bash
node scripts/verify.mjs fixtures
```

The Python verifier needs `cryptography`. From the repository root, install it into a virtual environment:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install cryptography
python3 scripts/verify.py fixtures
```

A Python marked as externally managed (PEP 668), such as Homebrew Python or the system Python of Debian and Ubuntu, refuses `pip install` outside a virtual environment with `error: externally-managed-environment`. The `.venv` directory is ignored by git. Activate it again in each new shell before running the Python tooling (on Windows, with `.venv\Scripts\activate`). On Debian and Ubuntu, `python3 -m venv` needs the `python3-venv` package. To use the system Python instead, install `cryptography` with your system package manager.

The top-level README's first command runs the parity gate without a clone:

```bash
pipx run --spec git+https://github.com/opena2a-standards/a2a-idf-conformance a2a-idf-conformance
```

pipx builds the package that [`pyproject.toml`](../pyproject.toml) defines from this repository, installs it with `cryptography` into a virtual environment of its own and runs its console script, `a2a-idf-conformance` ([`src/a2a_idf_conformance/__init__.py`](../src/a2a_idf_conformance/__init__.py)), which runs `parity.py` from the copy of the suite the wheel carries under `a2a_idf_conformance/suite/` in the repository's layout: `fixtures/`, `schemas/`, `vectors/`, `MANIFEST.sha256`, `verify.mjs`, `verify.py` and `parity/parity.py`. The generator, the profile script and the link check are not in the wheel; they run from a checkout. The package's description is the top-level `README.md` with each relative link rewritten to the file on GitHub (`blob/main/<path>` for a file, `tree/main/<path>` for a directory, the fragment kept) by the build hook [`hatch_build.py`](../hatch_build.py), which `pyproject.toml` names as hatchling's custom metadata hook, with `readme` listed under `project.dynamic`. PyPI renders a description with `readme_renderer`, which leaves a relative link as it is, so a link such as `./docs/coverage.md` would otherwise point under pypi.org, where there is no such page. `README.md` itself keeps its relative links, which GitHub resolves against the branch a reader is on and [`check-doc-links.mjs`](./check-doc-links.mjs) checks in the checkout. A link inside a fenced code block is not rewritten, and a link whose path is not in the checkout is rewritten all the same: the hook fails no build over a link, and [`parity/test_entry_point.py`](./parity/test_entry_point.py) checks that each rewritten path of `README.md` names a file or directory of the checkout. Both the wheel and the sdist write core metadata version 2.4 (`core-metadata-version` under each target in `pyproject.toml`): it carries every field the package sets, and twine 6.2.0, unlike twine 7.0.0, refuses the 2.5 that hatchling 1.32 writes by default as not a valid metadata version. The console script takes the options of `parity.py` (`--json`, `--verifier`), and like `parity.py` it needs `node` on the `PATH` for the Node verifier. In a checkout, `python3 -m a2a_idf_conformance` with `src/` on `PYTHONPATH` runs the gate of the checkout without an install.

Both verifiers accept fixture files or directories (walked recursively for `*.json`). A symlink to a directory met during the walk is not followed, so a fixture is not listed a second time under another name; a symlink to a fixture file is read, and a directory named on the command line is walked when it is a symlink. A `*.json` entry met during the walk that is neither a regular file nor a directory (a socket, a FIFO, a device) is reported as `ERROR` (`not a regular file`) and not read, so a FIFO cannot hold the run until a writer opens it.

## Output

Each verifier prints one block per fixture:

```
PASS  /abs/path/to/fixture.json
      observed: ACCEPT
```

Negative fixtures PASS when the observed rejection matches the pinned expectation:

```
PASS  /abs/path/to/signature-tampered.json
      observed: REJECT[SIGNATURE_INVALID]
```

On failure, the line is `FAIL` followed by `stage:` (which validation step failed) and `reason:` (the specific mismatch). The first stage is `schema`: each fixture is checked against its family's JSON Schema in [`../schemas/`](../schemas/), selected by the fixture's `$schema` URL, and a missing required field fails there (for example `reason: missing required field expected.signatureBase64`). The verifiers implement the keywords those schemas use (`type`, as one type name or a list of them, `const`, `enum`, `required`, `properties`, `allOf`, `if`/`then`); the schema test fails if a schema adds any other. A value of the wrong type is reported as, for example, `reason: crossSuiteEquivalence is present but is not a JSON object`.

When a verifier cannot evaluate a fixture at all, the line is `ERROR` followed by the error (the Python verifier prints its message; the Node verifier prints its message when it comes from a failed system call, such as opening a fixture path that does not exist, a file without read permission or a symlink loop, or listing a directory without read permission, or from an entry the walk does not read, and its stack trace otherwise, on one line with each line feed of the trace written as `\u000a`), with no `observed:` line:

```
ERROR /abs/path/to/fixture.json
      value type outside the fixture JCS domain: int
```

`ERROR` means the verifier raised instead of reaching a verdict: unreadable JSON (in both verifiers that includes a fixture holding `NaN`, `Infinity` or `-Infinity`, which are not JSON), or an attestation value outside the minimal JCS domain (numbers, booleans, null). A fixture missing a required block is not an `ERROR`: it fails at stage `schema`. A malformed level-fixture field is not an `ERROR`: it resolves to `REJECT[SHAPE_INVALID]`. That includes a lone surrogate in an organization attestation, which cannot enter the JCS form the attestation is signed over. A directory that cannot be listed is an `ERROR` under its own path, and so is each entry of a directory that can be listed but not searched (read permission without execute permission), whose status cannot be read and which may be a directory of fixtures, so a permissions problem cannot read as a pass. Neither verifier recurses on a fixture's nesting to read it, to check it against its schema (a schema reason names an array or an object by its JSON type, not by its contents), to word a reject reason (it quotes a string and names any other value by its JSON type, as in `unknown identityLevel: a JSON array`) or to write an attestation's JCS form, so in those steps nesting depth alone does not make either verifier raise. Nor does the length of an integer: both verifiers read an integer beyond the range of a double as an infinite number, which is not a JSON integer. A schema reason writes a number only when it is an integer of at most 2^53 - 1 in magnitude and names any other number by its JSON type (`a JSON integer`, `a JSON number`), so the two verifiers print the same reason. A reason that quotes a string as it is prints a lone surrogate in it, which UTF-8 cannot encode, as U+FFFD in both verifiers; a schema reason quotes a string as JSON text and writes a lone surrogate in it as a lowercase `\uXXXX` escape (`"X\ud800"`) in both verifiers. An `ERROR` counts as a fail.

Both verifiers write each C0 or C1 control character (U+0000 to U+001F, U+007F to U+009F) of a printed line as a lowercase `\uXXXX` escape, so a fixture value that a reason quotes cannot break a line of the report or send the terminal a command: a `publicKeyMultibase` of `z` followed by a line feed fails with `reason: invalid base58 character: \u000a`. In a printed line that is not JSON text, they also write a backslash followed by `u` as `\u005c`, and no other backslash, so a `\u` in such a line always begins an escape the verifier wrote: a `publicKeyMultibase` of `x` followed by the six characters `\u001b` fails with `reason: unsupported multibase prefix in x\u005cu001b`, and one of `x` followed by U+001B with `reason: unsupported multibase prefix in x\u001b`. A schema reason, and the `reconstructed:` and `expected:` lines that verify.mjs prints at stage `signature-base`, quote strings as JSON text, which writes a backslash as `\\` already, and keep their backslashes (a schema reason quotes `"X\\u001b"` and `"X\u001b"` for the same two values).

Both verifiers read a compact-form `publicKeyPem` by the same rules, and only the key bytes reach the crypto library. The first PEM block in the text is the one read, and it must be a `PUBLIC KEY` block that ends in its `END PUBLIC KEY` line; text before its BEGIN line and after its END line is not part of the key. Between those two lines, empty lines (or lines of spaces) may come before the base64 text, never within or after it, and the base64 text must be the encoding of a 44-byte Ed25519 SPKI key, character for character. Any other text fails at stage `public-key-extraction` with `reason: compact-form publicKeyPem is not an Ed25519 SPKI PEM`, so neither verifier reads past a block of another label, takes a private key or asks for a pass phrase.

The final line is `summary: N pass, M fail (T fixtures)`. Exit code is 0 if every fixture met its expected verdict (and reject category, when pinned), else 1. The parity gate parses the `PASS`/`FAIL`/`ERROR` lines and the `observed:` lines to assert cross-implementation agreement; an `ERROR` in one verifier and a verdict in the other is reported as a divergence.

## Testing another implementation

An A2A-IDF implementation joins the parity gate with `--verifier NAME=COMMAND` (repeatable). It is then run beside the two reference verifiers and compared with them and with the outcome pinned in each fixture:

```bash
python3 scripts/parity/parity.py --verifier mylib="node ../mylib/conformance.js" --json parity-report.json
```

The interface an implementation provides:

- **Invocation.** COMMAND is split with shell-style quoting (no shell is invoked) and run from the directory `parity.py` is called from, with the absolute path of this repository's `fixtures/` directory appended as its last argument. The implementation walks that directory recursively for `*.json` and evaluates every fixture.
- **Output.** On stdout, one block per fixture in the format shown under [Output](#output): a line `PASS <path>`, `FAIL <path>` or `ERROR <path>`, then, for `PASS` and `FAIL`, an indented line `observed: ACCEPT` or `observed: REJECT[CATEGORY]` (`CATEGORY` in upper case, letters and underscores, as in `rejectCategory`). `<path>` is the fixture path it was given (absolute), or any path whose last `fixtures` directory component is followed by the path under `fixtures/` (`fixtures/levels/x.json` and `/any/checkout/fixtures/levels/x.json` both name `levels/x.json`; `my-fixtures/levels/x.json` does not, because `my-fixtures` is a different directory name). Other lines are ignored. A line ends at a line feed (a carriage return also ends one); a line or paragraph separator (U+2028, U+2029) in a quoted fixture value does not.
- **Gate status.** `PASS` when the observed outcome matches the fixture's `expected` block (`verifyResult`, and `rejectCategory` when present), `FAIL` when it does not, `ERROR` when the implementation could not reach a verdict.
- **Exit code.** 0 when every fixture is `PASS`, non-zero otherwise.

The gate reports `PARITY: FAIL` and exits 1 when any verifier exits non-zero or cannot be started, misses a fixture or reports one that does not exist, disagrees with another verifier on gate status, verdict or reject category, or observes an outcome other than the one pinned in the fixture. The pinned check reads each fixture's `expected` block directly, so an implementation that prints `PASS` next to the wrong verdict still fails. A name already in use (`node`, `python`, or an earlier `--verifier`) is a usage error, exit 2. A fixture whose `expected` block is not a JSON object pins nothing, so the gate reports it as a divergence too.

## Cross-implementation guarantee

Both verifiers are wire-compatible with the [`envoys-rfc9421/`](https://github.com/aeoess/aps-conformance-suite) verifier on the signature-alone case (same keypair, same RFC 9421 components → byte-identical signature bytes). This is enforced twice: the generator asserts the recomputed signatures equal the Envoys §14 pins at generation time, and each fixture's `crossSuiteEquivalence.envoys` block makes the verifier check that the signature bytes it verified (parsed from `expected.signature`) match the pinned vector value, rejecting with `CROSS_SUITE_MISMATCH` when they do not. The `cross-suite-mismatch` negative fixture pins that check: its Signature header carries a different key's valid signature while `expected.signatureBase64` still carries the Envoys bytes.

## Why no implementation-library dependency

The conformance suite must not depend on any A2A-IDF SDK (including `@opena2a/a2a-idf`). Doing so would make the suite a self-verifier rather than an independent oracle. Both reference verifiers use only the platform's primitive cryptography (`node:crypto` / `cryptography`) plus inline RFC 9421, multibase, and minimal-JCS logic.
